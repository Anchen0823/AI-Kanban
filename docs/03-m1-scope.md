## 1. M1 到底要做完哪几件事

设计稿原文（§16）：

> 接入本地 MCP，在 Codex 和 Cursor 上完成真实检索与提案联调；对 Codex 用量接口进行只读探测，
> 支持时启用；不支持则记录原因并使用已验证导入。
>
> 退出条件：授权隔离、工具回执和接口版本记录完整；至少一条可重复的非手工采集路径有测试样本。
> WorkBuddy 以独立适配项推进，不阻塞已可用功能。

拆成四条可判定的东西：

| 目标 | 怎么算做完 | 本文对应章节 |
|---|---|---|
| 本地 MCP 传输层 | 真有个 stdio 进程实现了 JSON-RPC 2.0，六个工具可用 | §3 |
| 授权隔离 | 客户端怎么传参都不能越过凭据的项目范围，且留下拒绝日志 | §3.3 |
| 工具回执 | 失败时不回「看起来成功」的安慰文案 | §3.4 |
| 接口版本记录 | 每次调用/探测都记录客户端或服务端的真实版本号 | §3.3、§4.3 |
| 一条可重复的非手工采集路径 | 有固定 fixture、能反复跑出同样结论 | §4.4 |
| Codex / Cursor **真实联调** | 需要在真实客户端里配好后跑一次 | §6（**未完成**） |

前五条完成了，第六条没有。**这是一条很关键的界线：可重复 ≠ 已在真实客户端上验证。**
本项目对这个界线比较敏感，所以本文把两边分开写。

## 3. 本地 MCP 服务（`@aicc/mcp`）

### 3.1 为什么是「纯转发」

传输层里**不放任何业务判断**。权限、版本冲突、墓碑、上下文预算全留在服务端。

原因不是洁癖：一旦传输层和服务端各自判断一次，就存在两套口径，
而 MCP 这一侧的调用方是模型 —— 它读到的回执和自己以为的结果不一致时，
最难被人发现。六个工具每个都只是一个「MCP 参数 → 服务端请求体」的显式映射。

唯一的例外是**必填字段的本地校验**（比如 `memory_propose` 少 `title`）。
这类错误在传输层就拦下，理由见 §3.4。

### 3.2 协议实现要点

- **消息按行编码**，一行一个完整 JSON；不做 Content-Length 分帧
  （codex app-server 与多数 stdio MCP 实现都用换行分帧）。
- **版本协商**：客户端要求的版本受支持就原样回给客户端（不擅自升级）；
  不受支持时回退到本服务的最新版本，而不是报错断连。
- **`id` 为 0 的请求是合法请求**。早期实现把 falsy 的 `id` 当成通知丢掉了，
  这类 bug 不会报错，只会让某一个请求永远拿不到响应 —— 已经列为回归用例。
- **通知不产生响应**，包括 `notifications/initialized` 与 `notifications/cancelled`。
- 未 `initialize` 就调 `tools/list` / `tools/call` → `-32002`。
- 未知工具名 → `-32602`，并在文本里列出可用工具。
- `resources/*` 与 `prompts/*` 返回空列表，而不是「方法不存在」——
  空集是真的，报错会让某些客户端反复重试。

### 3.3 授权隔离

凭据的身份**只来自 `Authorization: Bearer`**。请求体里写「我是别的客户端」不会改变认定结果，
这一点同时有 HTTP 侧用例和 MCP 侧端到端用例（`test/mcp-e2e.test.ts`）覆盖。

六个工具与服务端 scope 一一对应；审批、删除、连接管理、备份恢复这几个动作
**不在 scope 枚举里**，所以结构上就不可选。

一个真实缺陷被这条纪律挡在了上线前：MCP 后端调服务端时漏了 CSRF 头，
结果拿到 403 `origin_rejected`。如果当时「顺手把 CSRF 校验放开」，
就等于为了内部调用把外部防线拆了 —— 正确做法是补 `x-aicc-request: 1`。

### 3.4 工具回执

失败回执里**不会出现**「已保存」「稍后可见」这类词。结构是固定的：

```text
<失败动作>（<code> / HTTP <status>）
<服务端原话>
细节：<结构化内容>
下一步：<可执行动作>
这次调用没有产生任何变更。不要向用户描述为已完成。
```

最后一句是给模型看的。它存在的理由是：模型倾向于把长文本回执里的任何正向词
当成成功信号，所以需要一句无法误读的话把整个回执钉死。

### 3.5 与 §11.2 签名的一处有意偏离

规范里写的是 `memory_propose(operation, project_id, content, sources?, base_version?)`，
缺了服务端必需的 `kind` 与 `title`。这里把它们提为**必填**，而不是替模型猜一个 ——
「AI 自动归纳出标题和类型」正是 §6.2 要挡掉的东西。理由写进了 `tools.ts` 的注释。

## 4. Codex 用量只读探测

### 4.1 它是怎么工作的

```text
spawn `codex app-server`
      ↓  initialize（记录 clientInfo / 协议版本）
      ↓  initialized 通知
   account/read                 确认登录状态与套餐（只读）
   account/usage/read           确认这个方法到底存不存在
   account/rateLimits/read      真正可用的那一个 → 落成额度快照
      ↓
   close（进程用完即关，不与用户正在用的 Codex 抢状态）
```

只调这三个查询方法，不触碰任何充值 / 重置 / 发信类方法（§3.2）。

### 4.2 实测结论（codex-cli 0.130.0）

设计稿 §3.2 提到的方法，在本机实测后的真实情况：

| 方法 | 实测结果 |
|---|---|
| `account/read` | **存在且可用** |
| `account/rateLimits/read` | **存在**，是可查询请求；本次因本机无外网访问而调用失败（记为 `unknown`，不是 `unsupported`） |
| `account/usage/read` | **不存在**。不在该版本的合法方法枚举里，请求会被 `methods_not_found` 拒绝 |
| `thread/tokenUsage/updated` | 存在但是**通知**，只对活动线程推送，不能当采集源 |

「不存在」和「存在但这次没调通」必须分开：前者是版本能力问题，后者是环境问题。
它们的修复路径完全不同 —— 前者要换方法，后者只要登录一下或者连通网络。

### 4.3 三种结论怎么落地

| 情况 | 写入的 `capability_status` | 说明 |
|---|---|---|
| 拿到额度窗口 | `verified` | 同时把版本号、三个方法各自的成败、合法方法数写进 `evidence` |
| 方法不在协议枚举里 | `unsupported` | 把该版本的合法方法列表作为证据留下 |
| 方法存在但调用失败 | `unknown` | 原因原样带上（未登录 / 无网络 / 进程没起来） |
| 本机没装 codex | `unknown` | **不能**说「不支持」—— 装一个就会改变结论 |

`capability_status` 改成 `verified` 时服务端强制要求有证据，没有证据会直接拒绝。
这条约束在 M0 就有，M1 的探测器是它的第一个真实使用者。

邮箱进证据前会脱敏（`a***@example.com`），完整地址不落库。

### 4.4 可重复的测试样本

`apps/server/test/fixtures/fake-codex-app-server.mjs` 假装自己是 codex app-server，
用同样的 stdio 协议回答。它覆盖四个分支：

1. 正常返回额度窗口 → `verified`
2. `methods_not_found` → `unsupported`（而不是 unknown）
3. 方法存在但报错 → `unknown`，且原因写明是环境/登录问题
4. 调用成功但没有窗口 → `unknown`，**不假装拿到了 0%**

探测器通过注入的 `spawnImpl` 接它，所以测试不需要真装 codex，
也不依赖网络。这就是退出条件里说的「至少一条可重复的非手工采集路径有测试样本」。

### 4.5 一个浮点坑

`1 - 0.42` 在 JS 里是 `0.5800000000000001`。
如果额度比例是「用 1 减已用」算出来的，这个尾巴会被写进 SQLite，
然后在某个界面上显示为 `58.00000000000001%`。

现在 `usedRatio` 与 `remainingRatio` 各自从整数百分比独立算出，存成干净的 `0.42` / `0.58`。
对应的回归用例在 core 的额度测试里。

### 4.6 安装与启用

需要本机有 Codex CLI（提供 `codex app-server`），并且 Codex 自己已登录。
然后在「设置与连接 → 能力登记」里对「Codex 用量接口」按一下探测。

**实测发现的一个坑**（与本项目无关，但会影响你后续挂 MCP）：
`codex` 的 `config.toml` 里如果有一行 **`service_tier="default"`**，
在 0.130.0 上会整个被判为无效配置（它只接受 `fast` / `flex`），
结果是 codex 放弃读取该配置文件 —— 那么通过 `codex mcp add` 写进去的 MCP 项也不会生效。
修完这一行再配 MCP。

## 5. 登记表单（超出设计稿 M1 的一块）

这件事不在 §16 的 M1 清单里，但它是「M1 之后能不能真的用起来」的前置条件：
客户端、计费账户、订阅这三个实体的写接口在 M0 就有了，却没有界面，
用户要绑定自己的 Codex / Cursor 之前得先手动 `curl` POST 一个 client。
它还会误导 —— 概览页显示「客户端 0」，看起来像是不支持，其实只是没法登记。

新增位置：「设置与连接 → 登记」。三条纪律：

- **金额不经过浮点。** 界面上填的是主单位小数（19.99），提交前用 core 的
  `moneyFromDecimal` 转成定点整数字符串（`"1999"`），并且**把中间值显示给用户核对**。
- **账户表结构上就没有凭据字段。** 界面连「登录 Cookie」的输入框都没有 ——
  不是忘了做，是设计上拒绝保存。
- **周期不知道就填「状态未知」。** 猜错会直接影响概览页的支出分桶。

### 6.1 为什么「真实联调」不算完成

设计稿的措辞是「在 Codex 和 Cursor 上完成**真实**检索与提案联调」。
本项目有一条硬纪律：**「内部能重复」不等于「外部已验证」**。

现在的状态是：

- ✅ MCP 服务端能握手、能列工具、能在真实 TCP + 真实凭据下被外部进程调用并拿到正确结果；
- ❌ 但没有在任何一个真实 AI 客户端的配置文件里挂载过、也没有用真实客户端跑过一次检索。

差的那一步需要你在自己机器上做，因为它涉及你的客户端配置。做完之后
「设置与连接 → 能力登记」里对应项的状态才能从 `documented` 变成 `verified`。
**在此之前它保持 `documented`，界面不会显示成「已同步」。**

## 8. 这一阶段抓到的缺陷

- **MCP 请求被分发两次。** 早期实现有一条同步 `handleLine` 和一条异步 `dispatchAsync`
  并行存在，为了让类型通过还写了 `null as unknown as` 这类断言。
  重写成单入口异步派发之后，这类 adapter 也一并删掉了。
  教训：**需要 `as unknown as` 才能通过的地方，通常是结构设计就有问题。**
- **float 尾巴**（§4.5）。
- **缺 CSRF 头导致 403**（§3.3）。
- **`id: 0` 被误判为通知**（§3.2）。
